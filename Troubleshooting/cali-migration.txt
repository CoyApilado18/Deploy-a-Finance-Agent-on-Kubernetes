WHY THIS MIGRATION
-------------------------------------------------------------------------
SYMPTOM
  The deployed finance-agent failed its first request with:
      Cannot connect to host generativelanguage.googleapis.com:443
      [Temporary failure in name resolution]
  From inside pods:
      internal names (finnhub-tools.kagent.svc..., kubernetes.default...)  resolve
      external names (googleapis.com, finnhub.io)                          FAIL
      1.1.1.1:53 and 8.8.8.8:53 (TCP)                                      reachable
      192.168.1.1:53 (home router)                                         timed out
  From the controlplane host itself, 192.168.1.1 answered DNS normally.
  CoreDNS logs, for every external name:
      read udp 192.168.49.85:51471->192.168.1.1:53: i/o timeout

ROOT CAUSE: pod network overlaps the home LAN
  - Calico IP pool default-ipv4-ippool = 192.168.0.0/16 (kubeadm podSubnet,
    controller-manager --cluster-cidr and kube-proxy clusterCIDR were all
    192.168.0.0/16 too).
  - The home LAN is 192.168.1.0/24 (router 192.168.1.1, nodes .107 and
    .225). It sits INSIDE the pod range.
  - Calico natOutgoing only SNATs traffic going to destinations OUTSIDE all
    Calico IP pools. 192.168.1.1 counted as "inside", so DNS packets
    reached the router with a pod source IP (e.g. 192.168.49.85). The
    router can't route the reply back, so every lookup timed out.
  - CoreDNS forwards external queries to the node's resolver
    (forward . /etc/resolv.conf -> 192.168.1.1), so ALL external DNS in
    the cluster failed, not just for the finance agent.

WHY 10.244.0.0/16
  Doesn't overlap the LAN (192.168.1.0/24), the Service range
  (10.96.0.0/12 = 10.96.0.0-10.111.255.255), or Docker's bridge
  (172.17.0.0/16). It's also the conventional kubeadm/flannel default.

ALTERNATIVE NOT CHOSEN (Fix A)
  Point CoreDNS at public resolvers (forward . 1.1.1.1 8.8.8.8). It's
  quicker, but it leaves the overlap in place, which also breaks any pod
  talking to other LAN hosts. You chose the proper fix.

  PROBLEM: kube-controller-manager went into CrashLoopBackOff
    Events: Liveness probe failed ... 127.0.0.1:10257 connection refused,
            BackOff restarting failed container
    Logs (--previous):
      "Error starting controller" err="failed to mark cidr[192.168.0.0/24]
       at idx [0] as occupied for node: controlplane: cidr 192.168.0.0/24 is
       out the range of cluster cidr 10.244.0.0/16"
       controller="node-ipam-controller"

    Cause: with --allocate-node-cidrs=true the controller-manager hands out
    node spec.podCIDR ranges from --cluster-cidr. On startup it found both
    nodes already holding 192.168.x ranges outside the new 10.244.0.0/16,
    and Kubernetes treats that as FATAL. (My earlier runbook wrongly said
    this would only cause harmless warnings.)

    Side effect while it was down: no Deployment/DaemonSet/ReplicaSet
    controllers ran, so the kube-proxy rollout restart stayed pending
    (pods were still 208 days old) and step 6 had to wait.

    Fix (run by you):
       sudo sed -i 's#--allocate-node-cidrs=true#--allocate-node-cidrs=false#' \
           /etc/kubernetes/manifests/kube-controller-manager.yaml

    never reads node spec.podCIDR. kube-proxy uses clusterCIDR, not node
    podCIDR. This is the usual setting for Calico clusters, and it avoids
    re-registering both nodes.

    Verified afterwards:

        --allocate-node-cidrs=false  --cluster-cidr=10.244.0.0/16

  d) kubeadm-config controllerManager.extraArgs (run by you)
     So that a future "kubeadm upgrade", which regenerates the
     controller-manager manifest with --allocate-node-cidrs=true, doesn't

-------------------------------------------------------------------------
LESSONS / NOTES
-------------------------------------------------------------------------
  - Never let the pod CIDR overlap the node/LAN network. Calico's
    natOutgoing exempts every address inside any IP pool, so LAN hosts
    inside the pod range become unreachable from pods.
  - A DISABLED Calico pool still counts for that NAT exemption. Delete the
    old pool once it's empty.
  - With --allocate-node-cidrs=true, changing --cluster-cidr while nodes
    hold podCIDRs outside the new range crashes kube-controller-manager.
    On Calico (calico-ipam) clusters, turn allocation off.
  - While kube-controller-manager is down, rollout restarts silently stay
    pending. Check it first if pods don't restart.
  - Joining a NEW node: with allocation off it gets no podCIDR. Calico
    doesn't need one.
  - Rollback to the old pool is no longer possible (it's deleted). The
    pre-migration configs are in ~/calico-migration/ for reference.
